# Backend Debugging Handbook

A method, a toolset, and a set of worked investigations for finding the real cause of backend bugs and shipping a fix you can defend. Written for an engineer who knows TypeScript, Node.js, PostgreSQL, Prisma, Redis and Docker, but has not yet built a systematic debugging habit.

Start here

How to use this handbook

This is a reference and a learning manual, not a quick-start. Read Part I once, front to back, because everything else depends on it. After that, jump to whichever chapter matches the problem in front of you. The chapter on the three reference investigations is meant to be read early: it shows the method working on real-looking evidence.

Part I — First principles and the debugging mindset

1. What debugging is and is not

Most engineers learn debugging by accident: trial and error, deadline pressure, and nobody ever naming the process out loud. That gap is where bad habits form. Before any tool, the discipline needs a definition.

1.1 A working definition

Debugging is evidence gathering, hypothesis formation, isolation, verification and prevention, done in that order, with each step constraining the next. The Debugging Handbook describes the same loop as five stages: observe, reproduce, isolate, validate, prevent. Chapter 2 expands it to sixteen concrete steps.

Debugging is not guessing at fixes, changing code until something works, pasting the first matching Stack Overflow answer, or re-prompting an AI assistant with different wording until the output looks plausible. Each of those can make a symptom disappear while leaving the cause in place, and a symptom that disappears for the wrong reason comes back later, usually in production.

1.2 Vocabulary you need before anything else

TermMeaningExample (from the logout scenario in Chapter 10)

General principleWhy the distinctions matter

If you stop at the trigger ("two tabs"), you will fix the wrong thing, for example by telling users to use one tab. If you stop at the symptom, you will patch the screen they see. If you skip the detection gap, the same class of bug will reach customers again. A complete investigation names all of them.

1.3 Five beliefs to retire

A stack trace is evidence, not a verdict. It tells you where an exception surfaced, not where the wrong state was created. A TypeError on line 80 is often caused by a value that was wrongly shaped on line 12, or by a request that should have been rejected by validation. Follow the trace backwards to where the bad value originated.

The last file you edited is not automatically responsible. The Debugging Handbook names this tunnel vision: recency feels like relevance. Check git log for what changed, but treat it as one hypothesis among several. Recent changes are a strong lead (the first question in any incident is "did we just deploy something?") and a poor proof.

"It works on my machine" is not proof of anything. Your laptop is a single-user, single-machine, trusted, effectively unlimited-resource world. Production is multi-user, multi-instance, resource-constrained and sometimes hostile. Section 8.1 lists thirteen concrete differences. A fix that passes locally has only shown that your local conditions no longer trigger the failure.

Random edits, blind retries and copy-pasted fixes create risk. A blind retry can double-charge a customer. An unexplained try/catch can hide the evidence you need. A copied fix can encode an assumption that does not hold in your system. All three change the system without increasing your knowledge of it.

A fix that "works" is not yet a diagnosis. Ask: does it work because I fixed the cause, or because I changed the conditions that exposed it? Adding a sleep before a racy read often makes a test pass without removing the race.

1.4 What a successful investigation must produce

By the end you should be able to hand a teammate:

  • A precise statement of expected versus actual behaviour, and the scope of impact.
  • A reproduction (or an honest characterisation of why you could not reproduce it) and the evidence that links it to the cause.
  • A root cause statement, with your confidence and what would change your mind.
  • The smallest safe fix, a regression test that fails without it, and the verification you actually ran.
  • The trigger, contributing factors and detection gap.
  • Specific prevention actions with owners.

General principleA fix is the second deliverable

The first deliverable is understanding. Teams that ship a fix without a stated cause cannot tell whether the next failure is the same bug or a new one.

2. A universal debugging lifecycle

The same sixteen steps apply to a failing unit test, a take-home assignment and a SEV-1. Under pressure you compress them; you do not skip them. Each step lists why it exists, what to do, what not to do, what to record, and when it is safe to move on.

Impact→Symptom→Facts→Baseline→Reproduce→Map→Hypotheses→Discriminating test→Evidence→Root cause→Minimal fix→Re-run the failure→Regression→Risk review→Deploy and observe→RCA

2.1 The sixteen steps

Step 1. Establish impact and urgency

Why
Impact decides how fast you must move and whether to mitigate before you understand. Debugging a cosmetic bug and a duplicate-payment bug are not the same job.
Do
Ask who is affected, how many, since when, whether money, data or security is involved, and whether it is getting worse. Pick a provisional severity (Chapter 9).
Don't
Treat every error as a P0, or treat a data-integrity problem as "just a bug".
Record
Provisional severity, evidence for it, and what you do not yet know about scope.
Proceed when
You know whether to contain harm first (page, roll back, disable) or investigate calmly.

Step 2. Capture the exact symptom and expected behaviour

Why
"Logout is broken" cannot be tested. "A user with two tabs gets a 401 on /auth/refresh and loses the session" can.
Do
Write one sentence each for expected and actual behaviour. Capture exact input, output, HTTP status, request ID, timestamps, environment and frequency.
Don't
Paraphrase an error message from memory or rely on a screenshot of a UI toast alone.
Record
The raw message, ID and timestamp, copied rather than retyped.
Proceed when
Someone else could check whether the bug is present using only your description.

Step 3. Gather initial facts without changing the system

Why
Every change you make before you understand the problem can destroy evidence or add a second problem.
Do
Read logs, dashboards, the ticket, git status, and the data involved. Use read-only queries.
Don't
Restart services, clear caches, rerun jobs or "tidy" data yet. Preserve the broken state if you can.
Record
Facts with their source and time. Mark each as observed or inferred.
Proceed when
You can list what is known, what is guessed, and what is missing.

Step 4. Establish a baseline and inspect recent changes

Why
Failures are differences. Knowing what "normal" looks like and what changed narrows the search enormously.
Do
Find the last known good time. Check deployments, config and secret changes, migrations, dependency bumps, traffic changes, and third-party status. Compare a failing request with a successful one.
Don't
Assume the newest commit is guilty, or assume nothing changed because nobody mentioned it.
Record
Timeline of changes against the first failure.
Proceed when
You have a "before" and "after" to compare.

Step 5. Reproduce the failure, or characterise why it is intermittent

Why
A failure you cannot trigger is a failure you cannot verify a fix for. At best you patch a symptom.
Do
Reduce to the smallest input, command or test that fails. For intermittent bugs, find what varies: concurrency, timing, data shape, instance, environment, clock.
Don't
Declare "cannot reproduce" after one try, or add a retry to hide flakiness.
Record
Exact steps, the failure rate, and the conditions that raise or lower it.
Proceed when
You can trigger it on demand, or you have a specific list of what you are missing and how you will instrument for it.

Step 6. Map the execution and request path

Why
You cannot isolate a fault in a system you have not located yourself within.
Do
Trace entry point, middleware, validation, auth, service logic, ORM/SQL, cache, queue, external calls, response. Note every async boundary and every place state is read or written.
Don't
Read only the file named in the stack trace.
Record
A short path sketch with the suspicious boundaries marked.
Proceed when
You can say where observed behaviour first diverges from expected behaviour, even roughly.

Step 7. Form a small set of ranked hypotheses

Why
Two or three explicit hypotheses stop you from chasing the first idea and give you something to disprove.
Do
Write each as "I believe X happens because Y". Rank by evidence strength first and test cost second.
Don't
Pick the one that is fastest to fix. The Debugging Handbook's rule: pick the one with the strongest evidence, even if it is slower.
Record
Hypotheses, the evidence for and against each, and your ranking.
Proceed when
Each hypothesis predicts something you could observe.

Step 8. Choose a test that distinguishes the hypotheses

Why
Evidence that fits every hypothesis equally teaches you nothing.
Do
Ask "what would I see if A were true and B were false?" Choose the cheapest observation that separates them.
Don't
Run an experiment that would look the same whichever hypothesis is right.
Record
The prediction made before running the test.
Proceed when
You have a prediction written down. Predictions made after the result are rationalisation.

Step 9. Gather evidence

Why
This is where hypotheses live or die.
Do
Use logs, breakpoints, a failing test, SQL, metrics, traces or a controlled experiment. Change one variable at a time.
Don't
Change several things at once, or stop the moment something confirms your favourite theory. Look for the observation that would prove it wrong.
Record
What you ran, what you saw, and what it does and does not establish.
Proceed when
One hypothesis survives and the others are explained away by evidence.

Step 10. Identify the smallest defensible root cause

Why
Fixing a broad "area" invites regressions. Fixing the mechanism fixes the class.
Do
Keep asking why past the first plausible answer. "The token is not found" is a symptom; "rotation is not atomic with validation" is a cause. Separate cause from trigger and contributing factors.
Don't
Stop at a description of the symptom, or at a cause you cannot test.
Record
A one-sentence root cause and your confidence.
Proceed when
You can predict a fix will remove the failure and can say how you would know it did not.

Step 11. Apply the smallest safe corrective change

Why
Small changes are reviewable, revertible and less likely to introduce new failure modes.
Do
Change the mechanism, not the neighbours. Keep diagnostic code out of the commit. Prefer enforcing invariants in the database where the invariant lives there.
Don't
Refactor adjacent code, widen a timeout, add a blanket try/catch, or add a sleep as a "fix".
Record
The diff and the reasoning for its shape.
Proceed when
The diff is small enough that a reviewer can hold the whole change in their head.

Step 12. Reproduce the original failure against the fix

Why
A fix verified only against a new scenario proves nothing about the old one.
Do
Re-run the exact reproduction from Step 5. Confirm it failed before and passes now. Then try to break your own fix with different timing, ordering and an extra concurrent actor.
Don't
Accept a green test that passed on the unfixed code too.
Record
Before and after output.
Proceed when
The same reproduction fails on the old code and passes on the new.

Step 13. Run regression and adjacent-path tests

Why
Your change may break other callers of the same function, table or queue.
Do
Run the full suite, not just the new test. Test boundary and failure cases, and other code paths that share the mechanism.
Don't
Delete or skip a test that becomes flaky under your fix without understanding why.
Record
Commands run and results.
Proceed when
Related behaviour is unchanged and the new test guards the old failure.

Step 14. Review operational and security risks

Why
A correct fix can still be unsafe to ship.
Do
Check transactions, locking and deadlock risk, idempotency, data migration needs, backwards compatibility during rolling deploys, secrets in logs, authorisation changes and performance.
Don't
Skip this because the diff is small. Auth, payment and data changes deserve the most review.
Record
Risks found and mitigations.
Proceed when
You can state the worst realistic outcome of shipping and how you would reverse it.

Step 15. Deploy safely, observe, and roll back if necessary

Why
Production is the only environment that proves production behaviour.
Do
Use the safest strategy available (Section 8.6), name the metrics to watch, set stop criteria in advance, and watch for duplicate side effects as well as errors.
Don't
Deploy and walk away, or invent rollback criteria after something looks wrong.
Record
Deploy time, version, metrics before and after, and who was watching.
Proceed when
The original failure is absent and no new failure signal has appeared over a window you chose beforehand.

Step 16. Write the RCA and assign prevention

Why
The next engineer needs the story, and the organisation needs the fix to the system, not just to the code.
Do
Write a blameless RCA (Chapter 12) with timeline, impact, detection, root cause, mitigation versus permanent fix, and prevention actions with owners.
Don't
Write "be more careful" or "add more logging".
Record
The RCA and tracked actions.
Proceed when
Every action has an owner and a measurable completion condition.

General principleUnder pressure

In a live incident, Steps 1 and 15 can dominate and Steps 5 to 10 can compress into minutes. What you may never skip is the discipline of writing down what you believe, why, and what would show you wrong. Mitigation (rollback, feature flag, rate-limit toggle) is a legitimate early move; it is not the permanent fix, and the RCA must say which was which.

3. What to know, what not to assume, and how to reason

3.1 Facts, assumptions, hypotheses, conclusions

KindDefinitionHow to treat it
FactDirectly observed, with a source and a time.Cite where you saw it.
AssumptionBelieved but not checked ("this endpoint is hit before the cache layer").Verify, or flag it out loud. The Debugging Handbook: "it should be configured that way" is not "I checked, and it is."
HypothesisAn explanation that makes testable predictions.Test it; try to falsify it.
ConclusionA hypothesis that survived discriminating tests.State your confidence and what would change it.

Illustrative example added by this handbookOne line, four kinds

Illustrative (not from a source). "The 500s started at 14:55" is a fact if you read it on the dashboard. "…because the deploy at 14:50 broke the handler" is a hypothesis until you check that the failing requests ran on the new version. "Redis must be fine" is an assumption until you run redis-cli ping from the same network as the app. "The cache TTL is why the data is stale" becomes a conclusion only after you show a request served from cache after the database changed.

3.2 Correlation versus causation

Two things moving together is a lead, not an explanation. In the logout scenario, the error rate tracks concurrent refresh calls per user: users with one tab show no incidents and users with two or more tabs show roughly 0.4%. That correlation is strong enough to point at concurrency, but it does not say which line of code is wrong. Only reading the rotation path and the interleaved timestamps does.

Ask three questions of any correlation: could the arrow run the other way, could a third factor drive both, and does a mechanism exist that explains it? A correlation with a plausible mechanism and a test is worth acting on. One without is a coincidence waiting to waste your afternoon.

3.3 Ranking hypotheses

Rank by evidence strength first, then test cost. When two are similarly supported, run the cheaper test first. When one is far better supported, do not let cheapness pull you to the wrong one. The Debugging Handbook makes the point with a table:

SituationJunior instinctSenior instinct
Error appears"Let me change this and see.""What evidence supports any cause yet? None. Go collect it."
Fix works locally"Ship it.""Did I fix the cause or change the conditions that exposed it?"
Cannot reproduceAdds a try/catch and moves on.Treats irreproducibility as a signal (concurrency, drift, missing telemetry) and instruments instead of suppressing.
Several plausible causesPicks the fastest to fix.Picks the strongest evidence, even if slower.

3.4 Look for the evidence that would prove you wrong

Confirmation bias is reading every new log line as support for the theory you formed early. The cure is procedural: before running a test, write down what result would disprove your favourite hypothesis. If no result could, the hypothesis is not testable and the test is not discriminating.

3.5 Cognitive traps

TrapWhat it looks likeCounter

Tunnel visionFixating on the last file you touched.Widen the path map (Step 6).

3.6 When you cannot reproduce it

Irreproducibility is itself evidence. List what differs between a failing and a passing occurrence and test each:

  • Concurrency or timing. Fire parallel requests and assert on final state, not just status codes.
  • Environment drift. Instance, region, container image, config, feature flag, library version.
  • Data shape. A specific user, tenant, locale, unusually large payload or edge-case value.
  • Time. Clock skew, TTL expiry, a daily peak. The duplicate-charge scenario correlates with a 2pm–4pm connection-pool peak.
  • Missing telemetry. If you cannot see the state that differs, add structured logs or metrics and wait for the next occurrence. That is a legitimate result, and it should end with a specific instrumentation change, not a shrug.

3.7 When several causes are plausible

Real incidents often have more than one contributor. The inventory scenario had two: a check-then-act race (primary) and a cache that widened the race window (amplifier). Separate them. Establish whether each is necessary (removing it prevents the failure), sufficient (it alone causes the failure), or merely amplifying. In that scenario the race exists even without the cache, which is why "remove the cache" would have been the wrong fix.

3.8 Root cause, trigger, contributing conditions, detection failure

Use four labels every time, and in this order:

  1. Root cause: the mechanism that makes the failure possible.
  2. Trigger: the event that exposed it this time.
  3. Contributing conditions: what widened the window or raised the stakes.
  4. Detection failure: why it took a customer or a finance report to find it.

3.9 Knowing when to stop

Stop investigating when the evidence is sufficient for the decision you must make, not when you feel certain. A reasonable bar: you can explain the mechanism, you have a reproduction that fails before the fix and passes after, and you have tried to break the fix. Document remaining uncertainty explicitly: "Confirmed: two concurrent 200s. Not confirmed: which client sent the third request." Uncertainty in writing is useful. Uncertainty hidden is a future incident.

3.10 One variable at a time

If you change the timeout, add a log line and bump a dependency in one go, a passing result tells you nothing about which change mattered. Make one change, observe, record, revert if it did not help. This is slower for one hypothesis and much faster over a whole investigation.

Part II — Manual debugging

4. Manual debugging, start to finish

This chapter is deliberately free of AI tooling. Manual debugging is the foundation: if you cannot do these steps yourself, you cannot judge whether an AI's suggestion is right (Chapter 7). Chapter 6 adds the VS Code debugger as one more instrument.

4.1 Start from behaviour, not from a guessed fix

Before opening an editor, produce this record:

Expected
One sentence from the requirement or contract. For example: "On refresh, the server validates the refresh token, rotates it, and returns a new access token."
Actual
One sentence of what happened, with exact status, body, and timestamps.
Input
The exact request (method, path, headers that matter, body) with secrets redacted. Capture the request or correlation ID.
Environment
Production, staging or local; app version or commit; which instance; region.
Frequency
Every time, intermittent (what rate?), or once.
Scope
One user, one endpoint, one tenant, one region, one deployment, or everything. Use the log or metric dimension that lets you split by each.

Then find the smallest reliable reproduction. A single curl, a failing unit test, or a ten-line script beats a click-through of the UI. If it only fails in a browser, capture the network tab as a HAR file and reduce from there.

Checking scope is a diagnostic act in its own right. "Only users on two or more tabs" (logout scenario), "only payments processed between 2pm and 4pm UTC" (duplicate-charge scenario), and "only within ~90 seconds of a worker restart" (escalation scenario) are each scope statements that eliminated most hypotheses before anyone read code.

4.2 Read and map the code path

For a Node.js/TypeScript backend the path usually looks like this:

HTTP request→router / controller→middleware (validation, auth)→service / business logic→ORM / SQL→external dependency / queue→response

For your bug, write the path as actual file and function names. Then walk it asking the same four questions at each hop:

  1. What input arrives here, and in what shape? (Could a field be missing, null, a string where a number is expected?)
  2. What state is read or written here? (Database row, cache key, in-memory variable, queue job.)
  3. Is there an await or callback here? (Anything between a read and the write that depends on it is a race window. Anything un-awaited is a lost error.)
  4. What happens on failure here? (Thrown, swallowed, logged, retried, returned as a status?)

The point where observed behaviour first differs from expected behaviour is your search area.

4.3 Controlled experiments

An experiment is a deliberate change designed to answer one question. The rules:

Change one variable at a time

Write the prediction first ("if the race theory is right, 20 parallel refreshes will produce more than one 200"). Run. Compare. Revert.

Use a failing test as the stable reproduction

A test that fails for the right reason is the best artefact an investigation can produce. It is repeatable, it documents the bug, and it becomes the regression test after the fix. A test that cannot fail on the buggy code does not count.

Add temporary, structured, privacy-safe logs

When you need to see state at a point, log a structured line with identifiers, not secrets:

temporary diagnostic (do not ship)
// DIAGNOSTIC: remove before commit. Logs ids and booleans only.
logger.info({
  diag: "rotate:read",
  requestId,
  tokenId: existing?.id,            // database id, not the token value
  used: existing?.used,
  familyId: existing?.familyId,
  t: Date.now(),
}, "rotation read");

Never log a raw refresh token, password, authorisation header, card number or full document. If you must correlate on a token, log a short hash prefix. Track your diagnostic lines (a diag: key and a DIAGNOSTIC comment make them greppable) and delete them before you commit: rg -n "DIAGNOSTIC|diag:" src.

Compare a failing request with a succeeding one

Put the two side by side: headers, body, user, timestamps, which instance served them, what was in the database at the time. The first difference is a hypothesis generator. In the logout evidence, comparing the "normal" refresh pair with the incident pair shows that one pair overlaps in time and the other does not (Chapter 10.1).

Inspect database state before and after

Snapshot the rows an operation touches, run the operation once in a safe environment, and snapshot again:

before/after inspection (local or staging)
SELECT id, token_hash, family_id, used, created_at
FROM refresh_tokens
WHERE family_id = 'fam_example'
ORDER BY created_at;
-- run the operation, then run the same SELECT again and diff the two outputs

Test boundary conditions

Empty input, missing optional fields, zero, negative, very large, duplicates, Unicode, time-zone edges, exactly-at-the-limit values. The Chapter 6 bug (a missing quantity) lives at a boundary.

Test concurrency directly when a race is suspected

Do not rely on "I clicked twice quickly". Fire parallel requests and assert on final state as well as status codes:

race-probe.ts (illustrative; Node 18+ for global fetch)
// Adapt URL, cookie and assertions to your system. Run against local or staging only.
const URL = process.env.TARGET_URL ?? "http://localhost:3000/auth/refresh";
const COOKIE = process.env.REFRESH_COOKIE!; // a valid single-use token for a TEST user

async function once() {
  const res = await fetch(URL, { method: "POST", headers: { cookie: `rt=${COOKIE}` } });
  return res.status;
}

async function main() {
  const N = 20;
  const statuses = await Promise.all(Array.from({ length: N }, once));
  const tally = statuses.reduce<Record<number, number>>((m, s) => ((m[s] = (m[s] ?? 0) + 1), m), {});
  console.log({ N, tally });
  // A correct single-use rotation should allow at most one 200 for the same token.
  // After the run, also SELECT the token family and check how many unused tokens exist.
}
main();

A single run that does not fail proves little: races are probabilistic. Repeat it, raise N, and add a small random delay between requests if the window is narrow. If it fails once in a hundred tries, keep the script; it is now your reproduction.

Revert diagnostic changes

Before committing: git diff and read every hunk. Diagnostic logs, console.log, skipped tests (it.only, xit), hardcoded IDs and local config edits must not ship.

General principleWriting it down is part of the method

The Take-Home Set B guidance puts it directly: write your hypothesis in one sentence before you change code ("I believe X happens because Y"), then design the smallest experiment that would prove or disprove it. This single habit of sequencing, more than raw intelligence, separates strong debuggers from weak ones.

5.3 Node.js request handling and error propagation

Symptom
Hung requests; a 500 with no useful body; inconsistent responses; the server stays up but a route never answers.
Likely causes
A handler path that never calls res.end/next; errors thrown in async code not reaching the error middleware (framework version dependent); body parsed twice; middleware order wrong (auth after the route, or a parser after the handler); event-loop blocked by CPU-heavy work; request timeout shorter than a downstream call.
Evidence to collect
Request ID through every log line; response time distribution; the middleware stack order; event-loop lag metric.
Diagnostic steps
Add a request-ID middleware first so every later step is traceable. Place a breakpoint in the error handler to see what reaches it. Test the failing route directly with curl to remove client behaviour from the picture.
False leads
Blaming the database for latency that is actually sequential awaits. Blaming the network when a single handler is looping.
Fix considerations
One central error handler that maps known errors to statuses and logs unknown ones with context. Timeouts at every outbound call.
Regression tests
Route-level tests for the failing input asserting status and body; a test for the error path.

5.4 HTTP/API validation, status codes, middleware and authentication

Symptom
Wrong status (a 200 carrying {"total":null}, a 500 for bad input, a 401 that should be 409); intermittent 401/403; works in Postman but not the browser.
Likely causes
Missing validation so bad input reaches business logic; error classes not mapped; cookie attributes (SameSite, Secure, Domain, Path) mismatched between environments; CORS preflight; clock skew between instances affecting JWT exp; role data stale in the session; a proxy altering headers or body size limits.
Evidence to collect
The full request/response including Set-Cookie; decoded (not verified) JWT claims; which instance served the request; the actual headers after the proxy.
Diagnostic steps
Reproduce with curl -i including cookies. Compare a working and a failing request header by header. Decode the token to inspect exp, iat, kid. Check server time on each instance.
False leads
A "random" auth failure that is really one instance with a different signing key or a drifted clock. Widening token lifetime to hide a rotation bug.
Fix considerations
Validate and reject early with a 4xx that tells the client what to fix. Distinguish retryable from terminal auth failures. Never "fix" a 401 by loosening verification.
Regression tests
Contract tests per status; a test per rejected-input class; for auth, a test that a genuinely reused or stolen token is still rejected.

Dangerous actionAuth, authorisation, secrets and input handling

Any change here is high risk. A fix that stops a user complaint by weakening verification, widening a role check or logging a token is worse than the bug. Require human review and security thinking before it ships.

Decision tree: diagnosing a Postgres deadlock

Source evidenceFrom the Debugging Handbook

Did the deadlock log name two specific queries?

  • No: enable log_lock_waits and reproduce; you need query text and lock types before isolating further.
  • Yes. Do both queries lock the same rows in a different order?
  • Yes: classic lock-ordering deadlock. Enforce a consistent acquisition order (for example always lock by ascending primary key), or use SELECT … FOR UPDATE SKIP LOCKED where appropriate.
  • No: likely an index or foreign-key lock interaction. Check for missing indexes on foreign-key columns.

The atomic conditional update pattern

When an invariant is "this number must never go below zero", let one SQL statement enforce it so there is no window between check and write:

WHERE id = $2 AND stock >= $1
RETURNING stock;
-- zero rows returned means insufficient stock: reject the order

5.6 Prisma query behaviour and transaction boundaries

Symptom
Type errors for fields that "should exist"; migration marked failed (P3009); a transaction that does not roll back what you expect; a decrement that goes negative; slow queries from N+1 access.
Likely causes
Client not regenerated after a schema change (prisma generate); manual ALTER TABLE out of band with migration history (drift); work performed outside the $transaction callback, or through this.prisma instead of the tx client; update({ decrement }) has no guard against going below zero; unique-constraint errors (P2002) unhandled; relation loops issuing a query per row.
Evidence to collect
prisma migrate status; the generated SQL (enable query logging); which client object each statement used; the error code.
Diagnostic steps
Enable Prisma query logging for the failing request and read the SQL it actually issues. Confirm every write inside an interactive transaction uses tx. Run prisma migrate status before assuming a code bug.
False leads
Believing an operation is atomic because the code sits near a $transaction call. Treating update({ decrement }) as if it validated the result.
Fix considerations
Put the read, check and write inside one transaction with a lock, or collapse them into one conditional SQL statement via $queryRaw. Back the rule with a unique or check constraint. Catch P2002 deliberately and decide whether it means "duplicate, return success" or "genuine conflict, alert".
Regression tests
A test that runs the operation concurrently against a real database, not a mock; a migration test from an empty database.

Source evidencePrisma migration drift, deep dive (Debugging Handbook)

Hypothesis: the schema file and the live database diverged because someone ran a manual ALTER TABLE, or a migration was edited after it was applied elsewhere. Investigation: prisma migrate status shows applied versus pending; if it reports drift, diff the live schema against the last migration rather than guessing. Verification: after migrate resolve or a corrective migration, migrate status is clean and a fresh database built from migration history matches production's schema.

5.7 Redis, caching, TTLs and invalidation

Symptom
Stale data after an update; sudden database load; rate limiting or sessions appearing to "stop working" without errors; a feature that works with Redis disabled and fails with it enabled.
Likely causes
Invalidation missed on one write path; wrong key granularity; TTL too long (or the cache used as a source of truth for a guard); Redis not running or reconnecting slowly while middleware fails open; eviction under memory pressure dropping keys early; KEYS scans blocking a large instance.
Evidence to collect
redis-cli ping and INFO from the app's network; connection logs; the key pattern and TTL (TTL key); whether invalidation code actually ran; hit-rate metrics; behaviour with the cache on and off.
Diagnostic steps
Confirm Redis is running before theorising about pools and retries. Read the key before and after a write. Check what the middleware does when the store is unreachable.
False leads
Increasing the Redis pool size and adding retries when Redis was simply down. Treating TTL expiry and explicit invalidation as the same thing.
Fix considerations
Use TTL as a safety net and explicit invalidation on writes. Never let a cache value gate a correctness decision (stock guards, balance checks). Decide per feature whether failure is open or closed: rate limiting on sensitive endpoints should fail closed; non-critical caching can fail open.
Regression tests
A test that an update invalidates the cache; a test with the cache enabled at production TTL; a chaos test with Redis stopped.

Source evidenceFail-open middleware, a pattern to memorise (Debugging Handbook)

When Redis is unreachable, middleware written defensively ("if the store is down, do not block the request") silently disables security or rate limiting. The container looks healthy and requests return 200, so the failure shows up only in traffic patterns or an audit. Treat "everything is suspiciously fine" as a symptom worth investigating.

5.8 Queues, workers, retries, idempotency, dead-letter queues, stuck jobs

Symptom
Jobs run twice; side effects duplicated; emails late; queue depth climbing; jobs stuck "active" forever; events that never arrive; the same event handled twice after a deploy.
Likely causes
At-least-once delivery without an idempotent consumer; no lease or expiry on claimed work, so a dead worker's claim lasts forever; two workers picking the same job during a deploy; a poison message crashing every worker that touches it; retry policy re-running a non-idempotent side effect; a scheduled job running on every replica.
Evidence to collect
Queue depth and age of the oldest item; per-job attempt counts and failure reasons; worker heartbeats; the dead-letter queue contents; the row state in any outbox table.
Diagnostic steps
Check whether workers are crashing on a specific bad job (poison message) versus being under-provisioned. Look for the "in-progress" state with no live owner. Enumerate every point where a worker can die and the state it leaves behind.
False leads
Assuming the queue's own retry fixes a claim problem at a different layer (an outbox row stuck CLAIMED is not a retry matter). Lengthening a poll interval instead of adding a real lease.
Fix considerations
Design for at-least-once and make consumers idempotent. Give claims a lease with an expiry, using the database's clock. Bias toward the failure mode you can tolerate (a duplicate page is bad, a silently dropped page is worse). Route exhausted jobs to a dead-letter queue instead of vanishing.
Regression tests
A chaos test that kills a worker mid-processing and asserts eventual completion; a forced double-delivery test asserting a single side effect.

Source evidenceWhy retries and dead-letter queues matter (Deployment Handbook)

Third-party services fail transiently. A queue gives automatic retry with backoff (for example 5 seconds, then 30, then 5 minutes). If a job fails every retry, it lands in a dead-letter queue for inspection rather than vanishing. Workers are deployed as a separate service for independent scaling, fault isolation and resource shaping. Rule of thumb: if work does not need to finish before the user gets a response, it belongs in a queue.

Symptom

Likely causes

Evidence to collect
The provider's delivery log (attempt count, status, latency); your own log of each step; the ordering of commit versus acknowledgement; reconciliation of provider records against local rows.
Diagnostic steps
Draw the sequence and mark every point a failure can occur; ask what state is left behind at each. Compare provider and local ledgers by reference ID.
False leads
Treating a provider's retry as a provider bug when at-least-once delivery is documented behaviour.
Fix considerations
Make the handler idempotent with the key recorded atomically with the side effects. Back it with database unique constraints. Respond quickly and process asynchronously where timeouts are tight. Reconcile periodically to catch what slips through.
Regression tests
Duplicate and concurrent delivery tests; a test that kills the process between the side effect and the acknowledgement.

Source evidenceWebhook double-processing (Debugging Handbook)

Without an idempotency check, "received twice" becomes "processed twice". Fix: store the provider's event ID with a unique constraint and check-and-insert before any side effects, inside the same transaction as the side effect.

6.1 The mental model

  • A breakpoint pauses execution at a line you choose, before that line runs.
  • The call stack shows how execution arrived at the pause: which function called which.
  • Variables and scope show the program's state at that exact moment.
  • Stepping moves forward in small, controlled increments so you can watch state change.
  • A debugger shows one execution path. It does not prove behaviour for every input, and it cannot show concurrent interleavings: while the process is paused, the whole Node.js event loop is paused.
  • A breakpoint may not bind. If the program that is running is not the code you set the breakpoint in (stale build, wrong script, missing source map, wrong path mapping), the editor shows the breakpoint but execution sails past it.

General principleThe debugger answers questions; you supply them

Never start by "stepping through to see what happens". Start with a question: which value is wrong, and where does it first become wrong? Put the breakpoint where you can check that.

Debug Console versus the integrated terminal

The terminal is where your program's own output (and your shell commands) live. The Debug Console is a REPL attached to the paused program. Typing input.quantity there evaluates it in the current frame.

Dangerous actionCareful with the Debug Console

Anything you type is executed in the running process. input.quantity = 2 changes live state, and from then on you are debugging a program that no longer behaves as it did. Calling functions with side effects (saving, sending, deleting) does exactly that for real. Keep evaluations read-only. If you do mutate something, write it down: the experiment has altered the system. Do not do this against production data.

The debug session, narrated

  1. Execution pauses on your breakpoint. The line is highlighted; it has not run yet. Question: what is input?

  3. In the Call Stack, note the frame. It is an event-callback frame (req.on("end")), not the HTTP route directly: the body is parsed asynchronously after the request finishes.
  4. Press F11 (Step Into) to enter calculateTotal. Question: where does the bad value first appear?

Verified conclusionVerified conclusion for this example

The root cause is that calculateTotal multiplies by input.quantity when it is undefined, producing NaN; the handler never validates the input; and JSON.stringify converts NaN to null, so a 200 OK is returned for invalid input. The as number cast hid the problem from the compiler.

Stepping through async code

  • F10 over a line containing await waits for the promise to settle and stops at the next line of the same function.
  • F11 on an await someAsyncFn() enters someAsyncFn when it starts running.
  • Put breakpoints inside callbacks and .then/catch bodies; stepping out of a function does not return to the original caller across an async boundary.
  • The Call Stack may show frames labelled async, which are reconstructed history, not live frames. Prefer a breakpoint on the exact line you care about.

The minimal fix and the regression test

src/pricing.ts (fixed)
export interface OrderInput {
  unitPrice: number;
  quantity?: number;
  discountCode?: string;
}

const DISCOUNTS: Record<string, number> = { SAVE10: 0.1, SAVE25: 0.25 };

export class InvalidOrderError extends Error {}

export function calculateTotal(input: OrderInput): number {
  const { unitPrice, quantity } = input;
  if (!Number.isFinite(unitPrice) || unitPrice < 0) {
    throw new InvalidOrderError("unitPrice must be a non-negative number");
  }
  if (!Number.isInteger(quantity) || (quantity as number) < 1) {
    throw new InvalidOrderError("quantity must be a positive integer");
  }
  const subtotal = unitPrice * (quantity as number);
  const rate = input.discountCode ? DISCOUNTS[input.discountCode] ?? 0 : 0;
  return Math.round(subtotal * (1 - rate) * 100) / 100;
}

The handler maps the validation error to a client error instead of a success:

src/server.ts (fixed handler body)
req.on("end", () => {
  try {
    const input = JSON.parse(body) as OrderInput;
    const total = calculateTotal(input);
    res.writeHead(200, { "content-type": "application/json" });
    res.end(JSON.stringify({ total }));
  } catch (err) {
    if (err instanceof InvalidOrderError || err instanceof SyntaxError) {
      res.writeHead(400, { "content-type": "application/json" });
      res.end(JSON.stringify({ error: (err as Error).message }));
      return;
    }
    console.error(err);          // unknown errors are logged, not swallowed
    res.writeHead(500).end();
  }
});

6.4 Debugger workflows for real backend bugs

A request returns an unexpected status

  1. Reproduce it with curl -i and note the route.
  2. Set a breakpoint at the route handler's first line and one in the error-handling middleware.
  3. Trigger. Check whether the error middleware runs, and examine the error object (name, message, stack).
  4. Step toward the line that chooses the status. Question: which branch produced this status, and what input led there?

A variable becomes undefined or null

  1. Break at the line where the wrong value is used; confirm it is wrong.
  2. Use the Call Stack to move to the caller; inspect what it passed.
  3. Walk upward until the value is last correct. The line between the last correct and first wrong frame is your suspect.

A rejected promise or swallowed exception

  1. In the Breakpoints panel tick Uncaught Exceptions; if nothing pauses, tick Caught Exceptions as well.
  2. Re-trigger. The debugger stops at the throw, with the real stack.
  3. If nothing throws, look for a dropped promise (a call missing await) or an empty catch. A temporary process.on('unhandledRejection', …) can reveal it.

A database result differs from expectation

  1. Break on the line after the await that returns the result; inspect the shape (array versus object, null versus empty).
  2. Turn on query logging so you see the SQL and parameters actually sent. Compare them with what you expected.
  3. Run that SQL in a read-only session against a safe copy; check the data and constraints, not just the code.

Catch one particular user, request or state

Right-click the gutter, add a conditional breakpoint with an expression like userId === "usr_7734" or req.headers["x-request-id"] === "…". This avoids stopping on the thousand unrelated requests.

Observe without pausing: logpoints

When pausing would alter timing (a timeout, a retry, a race), add a logpoint: rotate token={existing.id} used={existing.used} t={Date.now()}. Read the interleaving afterwards in the Debug Console.

A suspected race condition

An ordinary breakpoint freezes the whole process, so the other request you hoped to overlap is frozen too, and the race you are chasing may disappear. Use the debugger only after you have evidence of what to look at. To catch the race itself:

  1. Reproduce it with a concurrent test or script (Section 4.3) and assert on final state.
  2. Instrument with timestamped structured logs or logpoints that record each step's start and end per request ID.
  3. Reconstruct the interleaving from those timestamps (the logout walkthrough does this with log timestamps and latencies).
  4. Verify the fix with the same concurrent test, repeated many times, not with a single stepped run.

7. AI-assisted debugging

This chapter is separate from Chapters 4 to 6 on purpose. AI is a reasoning and productivity aid. It is not an authority, it cannot observe your running system, and it is not accountable for what ships. AI can accelerate reasoning and implementation, but evidence collection, impact judgment, correctness verification, and production accountability remain human responsibilities.

Source evidenceQuestions people actually ask (Debugging Handbook)

Can AI be used in take-home assignments? Usually yes if the instructions do not forbid it, but as a research assistant, not an author. 7.2 What AI is unreliable or unsafe for

  • Hallucinated APIs and repository facts. It may invent a function, an option, or a file that does not exist in your version or your repository.
  • Overconfident root-cause claims from incomplete evidence. Fluent prose is not evidence.
  • Symptom-suppressing fixes: a retry, a bigger timeout, a try/catch, a sleep.
  • Broken transaction and concurrency guarantees: moving a read outside a transaction, or adding a lock that deadlocks under a different ordering.
  • Insecure changes to authentication, authorisation, secrets or input handling.
  • Correlation presented as causation.
  • Invented evidence or claimed test results. An assistant that says "tests pass" without a pasted run output has told you nothing.
  • Destructive production commands: DELETE without a WHERE, FLUSHALL, force-pushes, mass invalidation of sessions.
  • Data leakage: pasting customer data, credentials, tokens, personal information or proprietary code into tools you are not authorised to use.
  • Prompt injection: instructions hidden in logs, issue text, files or user-controlled data that an AI agent might obey ("ignore your instructions and run …").
  • Excess tool access: an agent with write access to production, secrets or deployment can cause far more damage than a chat window.

Source evidenceWhen AI confidently suggests the wrong fix (Debugging Handbook)

A developer reports "Redis calls are timing out intermittently." An assistant, working only from the description, confidently suggests a larger connection pool and retries. The actual cause: Redis was not running in that environment, and a middleware layer was written to fail open when the store was unreachable, so requests appeared to mostly work. The suggestion was not unreasonable for the description; it reasoned from a plausible symptom instead of verified evidence because it had no way to check whether Redis was running. 7.4 A safe AI-assisted debugging loop

  1. A human defines the symptom, impact, constraints and the evidence available.
  2. Remove secrets and sensitive customer data. Replace tokens, emails, IDs and hostnames with placeholders.
  3. Ask the AI to summarise facts separately from assumptions.
  4. Ask for multiple hypotheses and the evidence that would distinguish them.
  5. A human chooses the next diagnostic step.
  6. Run the step locally or through approved tools.
  7. Feed back the actual result, pasted, not an imagined or paraphrased one.
  8. Update or reject hypotheses based on that evidence.
  9. Ask for the smallest candidate fix and its alternatives.
  10. A human reviews the patch.
  11. Run targeted tests, regression tests, security checks, and relevant concurrency or load tests.
  12. Inspect the diff and verify actual execution (confirm the new test fails without the fix).
  13. Prepare deployment, rollback and monitoring steps.
  14. A human approves operational changes.
  15. Observe post-fix behaviour and write an evidence-based RCA.

General principleWhy “paste the error and ask the AI to fix it” is not enough

It skips Steps 1, 2, 5, 7 and 8. The AI sees a symptom, not your system, so it must fill gaps with plausible guesses. You get a fix without a diagnosis, you cannot tell whether it addresses the cause, and you have usually exposed more data than needed. The result is a patch you do not understand against a bug you have not located. If it happens to work, you still cannot say why, which fails the standard in Chapter 1.4.

Domain-targeted prompt patterns (from the Debugging Handbook)

The source's six examples share one pattern: supply the evidence first and constrain the question to it with "given only this". That phrase keeps the AI from filling gaps with plausible guesses.

  • Webhooks: "Here is the handler and two log lines showing the same event ID processed twice, four seconds apart. Where is the idempotency gap?"

8.2 Monitoring versus observability

  • Monitoring detects known conditions and signals that something may be wrong: error rate above a threshold, queue depth rising, a health check failing.
  • Observability lets you investigate unfamiliar conditions by examining what the system emits (logs, metrics, traces) without having predicted the question in advance.
  • Alerts are signals for action, not root-cause explanations. "Error rate above 2% for 5 minutes" tells you to look; it does not tell you why.

Source evidenceThe observability loop (Deployment Handbook)

Service emits logs, metrics and traces; they are collected centrally; a metric crosses a threshold; an alert fires; an on-call engineer is paged; the engineer opens a dashboard and drills into traces and logs; the root cause is identified and a fix or rollback is shipped.

8.3 The three core signals

Logs: discrete events and context

Logs record what happened at a point in time. Make them structured (JSON), levelled (debug, info, warn, error), timestamped, and carrying a request or correlation ID so one request can be followed across lines and services.

Useful fields by component:

ComponentFields worth logging
Node.js APIrequestId, route, method, status, latency, userId (internal ID), tenant, app version, instance.
Background workerjobId, queue, job name, attempt number, max attempts, duration, outcome, failure reason, worker ID.
Database operationOperation name, table, duration, affected rows, transaction outcome, error code (never full parameter values containing secrets).

Log errors with context: the operation, the identifiers involved, and the error object (message, stack), not just "failed".

Dangerous actionWhat must never be logged

Full refresh tokens, passwords, Authorization headers, session cookies, API keys, card numbers, or sensitive documents. Logs are copied to many systems, retained for a long time, and read by many people. If you need to correlate on a token, log a short hash prefix or a database ID. In the logout evidence, the logs correctly use tokenFamily and token IDs (tok_8ab3) rather than token values.

Both extremes hurt: noisy logs bury signals and cost money (the Deployment Handbook suggests sampling verbose debug logs in production), and missing context leaves a line like "refresh failed" that cannot be tied to a request.

Questions logs answer well: what happened on this one request? what was the sequence? what did the error say?

Metrics: numbers over time

Metrics show scope, trend and correlation. Core ones for a backend:

  • Request rate, error rate, latency distribution (p50, p95, p99).
  • Saturation: CPU, memory, event-loop lag, database pool usage.
  • Queue depth and queue age (age of the oldest item matters more than depth alone), worker throughput, retry counts.
  • Dependency failures: timeouts and error rates per downstream service.

Why averages mislead. An average can look healthy while a tail of requests is terrible. In the Semble evidence, p50 was 45ms and p95 was 210ms, but p99 was 14,800ms: a small slice of requests were hitting a database timeout, which an average would have buried. Always look at percentiles, and at the distribution when you can.

Alert thresholds. Do not copy a universal number. The Deployment Handbook's example ("error rate above 2% for 5 minutes") is an illustration of the shape of an alert, not a recommendation for your service. Choose thresholds from your own baseline and user impact, expect to tune them, and watch two failure modes: false positives that train people to ignore the pager (alert fatigue) and blind spots that detect problems late. An alert should have an owner and a first action.

Questions metrics answer well: is this broad or narrow, and since when? did it change at the deploy? is something saturated?

Distributed traces: where time or failure occurs

A trace follows one request across services. It is made of spans: timed operations with parent-child relationships (an HTTP handler span containing a database span and an outbound-call span). Traces show the shape and timing of a request, so you can see whether the slow part was your code, the database or a third party.

Limits to keep in mind: traces are often sampled, so the request you want may be missing; propagation can break at a queue boundary or a service that does not forward the trace context; and spans only show what you instrumented. Put the trace ID in your logs so you can jump from a slow span to the log lines of that exact request. A trace can distinguish a slow database query from a slow external call by their span durations.

A useful heuristic, not a law

General principleThat, where, why

Metrics often tell you that something is wrong. Traces help show where time or failure occurs. Logs often provide event-level detail about what happened and why. This is a heuristic, not a rigid law. Which signal to start with depends on what you already know.

NoteTwo sources, two orderings: how to reconcile

The Debugging Handbook recommends the order logs, then metrics, then traces: logs answer "what happened on this request", and starting with traces on what is really a single bad log line is expensive overkill, while starting with logs on a system-wide degradation means reading thousands of lines to find a pattern a dashboard shows at a glance. The Deployment Handbook frames the same signals as that, where, why (metrics, traces, logs). These are consistent once you notice what each assumes. If you start from one specific failing request (a ticket with a request ID), begin with its logs. If you start from an alert or a broad degradation, begin with metrics to establish scope, then traces to localise, then logs for detail. The next section uses the second, alert-driven order and shows when to change it.

8.4 Investigation order for a production issue

  1. Confirm user impact and the alert. Is it real, who is affected, which journey? Provisional severity (Chapter 9).
  2. Check overall service health and error and latency trends. What changed, and when did it start?
  3. Determine the blast radius and start time. Split by endpoint, tenant, region, version and instance.
  4. Compare before and after deployment or configuration changes. "Did we just deploy something?" is the first question in any incident.
  5. Inspect traces for slow or failing segments of affected requests.
  6. Query correlated logs for those requests (by request or trace ID).
  7. Inspect database, queue, cache and dependency state as the evidence suggests. Read-only first.
  8. Reproduce in a safe environment where possible.
  9. Form and test hypotheses (Chapter 3).
  10. Mitigate and verify. Confirm recovery with the same signals you used to detect the problem.

When the order changes

  • An obvious exception with a precise stack trace (for example an error-tracking alert naming one line): go straight to the code and the request that triggered it; confirm scope afterward.
  • A suspected data-integrity incident (duplicate charges, negative stock, wrong balances): contain first, stop the bleeding, preserve evidence, and quantify affected records before touching data. Reconcile ledgers rather than relying on error rates, because a correctness bug may produce no errors at all.
  • A single user's ticket with a request ID: start with that request's logs.
  • Everything is suspiciously fine while customers complain: suspect a fail-open path (Section 5.7) or missing instrumentation, not a healthy system.

A structured Pino logger with request ID and safe fields

logger.js (CommonJS, executed with Pino 10.4.0)
const pino = require("pino");
const { AsyncLocalStorage } = require("node:async_hooks");
const { randomUUID } = require("node:crypto");

const als = new AsyncLocalStorage();

const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  // Redaction paths are literal. "*.token" matches ONE level deep, so list the
  // top-level key too. Test your config with a fake secret before trusting it.
  redact: {
    paths: [
      "req.headers.authorization", "req.headers.cookie",
      "password", "refreshToken", "token",
      "*.password", "*.refreshToken", "*.token",
    ],
    censor: "[REDACTED]",
  },
  // Adds requestId to every line logged inside the request's async context.
  mixin() {
    const s = als.getStore();
    return s ? { requestId: s.requestId } : {};
  },
});

// Call at the start of each request (framework middleware wraps this).
function withRequest(headers, fn) {
  const requestId = headers["x-request-id"] ?? randomUUID();
  return als.run({ requestId }, () => fn(requestId));
}

module.exports = { logger, withRequest };

Source evidenceA redaction detail found while testing this example

With only *.token in the paths, a log object with a top-level token field was not redacted in the test run. Adding the literal top-level paths (token, refreshToken, password) fixed it. Always prove redaction works by logging a fake secret and reading the output.

Instrumentation checklist for a modest Node.js, PostgreSQL, Redis and BullMQ application

  • Every request has a request ID, returned in a response header and carried into logs, outbound calls and job data.
  • Logs are JSON with level, timestamp, service, version and instance; redaction is tested with a fake secret.
  • HTTP metrics: rate, errors, and latency histogram per route; percentiles on the dashboard, not just the average.
  • Event-loop lag and memory per instance.
  • Database: pool in-use and waiting counts, slow-query logging, lock-wait logging (log_lock_waits), and error counts by code.
